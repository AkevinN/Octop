# 需求文档：统一认证适配器

> spec：`p2-11-identity-adapters` ｜ 波次：二期 ｜ 基线：`757fd12` ｜ 预估：7 人日
> 前置：`w3-04-session-and-password` ｜ 全局约束：`.kiro/steering/intranet-transformation.md`

## 引言

`w3-04` 已把登录模式收口为 `local / sso_only / hybrid` 三态，并交付会话表、短时令牌与口令策略；`w3-04` 假设统一认证走 OIDC（steering D1 默认假设）。本 spec 只在**行方最终答复"行内统一认证不是 OIDC"**时才启动，覆盖 D1 列出的三种替代协议：CAS 3.0、SAML 2.0、LDAP/AD。三者互斥——行方只会选其中一种落地，故本 spec 按协议拆成三个独立估算单元，实施时只取行方选中的一个。

范围内：
- CAS 3.0：新增 `CasAdapter`，贴合现有 `IdentityProvider` 协议（`src/octop/infra/auth/sso/providers/base.py`），复用 `w3-04` 已交付的登录/会话/吊销链路。
- SAML 2.0：新增 `SamlAdapter`，同样贴合 `IdentityProvider` 协议，但依赖 `xmlsec` 系统库做 XML 签名与加密断言校验，离线部署与信创 CPU 架构风险最高，需单独评估可行性。
- LDAP/AD：不贴合 `IdentityProvider` 协议（该协议是"浏览器重定向 + 授权码"形状，LDAP 是直接口令 bind），在 `infra/users/manager.py::UserManager.authenticate` 内新增外部目录 bind 分支。
- IdP 使用 SM2 签名验证时，签名算法适配与 `p2-02-kms-sm-crypto` 协作（`p2-02` 提供 `CryptoProvider` 国密后端，本 spec 只负责在验签点接入对应算法标识，不重复实现国密原语）。

范围外（归其他 spec）：
- OIDC 本身的加固（issuer 校验、算法白名单、准入组/角色映射）——归 `w3-04`（`w3-04` 已交付，本 spec 只消费其登录模式开关与会话表，不重复实现）。
- 会话表、短时令牌、吊销、口令策略——归 `w3-04`，本 spec 的三种适配器登录成功后统一走 `w3-04` 的签发/吊销路径，不新建平行机制。
- 国密算法原语（SM2/SM3/SM4 实现、KMS/SDF 对接）——归 `p2-02`，本 spec 仅在 IdP 要求 SM2 验签时调用 `p2-02` 暴露的接口。
- 三员分立、权限键治理——归 `w3-03`，本 spec 不新增角色模型，只把 IdP 返回的组映射到 `w3-04`/`w3-03` 已有的角色体系。

## 需求

### 需求 1：CAS 3.0 适配器（若行方选择 CAS）

**用户故事：** 作为行内运维人员，我希望 Octop 能通过 CAS 3.0 协议对接行内统一认证平台，以便员工用现有 CAS 账号登录 Octop 而无需另建账号体系。

#### 验收标准
1. 当管理员在 SSO 设置中新增 kind 为 `cas` 的 provider 并保存时，系统应当在 `SSO_KINDS`、`auth_oauth.py` 的 `SsoKind` 类型、`build_adapters`、前端 kind 枚举与对应 i18n 中都能识别该 kind（不遗漏任一注册点）。
2. 当用户访问 CAS 登录入口时，系统应当跳转到 CAS 的 `/login?service=` 地址。
3. 当 CAS 侧回调携带 `ticket` 参数时，系统应当调用 `/p3/serviceValidate` 校验该票据，校验通过后按 `IdentityProvider.complete_login` 契约签发用户身份，并交给 `w3-04` 的会话签发流程。
4. 如果 CAS 票据校验失败或过期，那么系统应当拒绝登录并返回可本地化的错误提示，不创建会话。
5. 系统应当始终把 CAS 登录成功后的令牌签发、会话记录、吊销行为委托给 `w3-04` 已交付的机制，不新建平行的令牌或会话存储。

### 需求 2：SAML 2.0 适配器（若行方选择 SAML）

**用户故事：** 作为行内运维人员，我希望 Octop 能通过 SAML 2.0 协议对接行内 IdP，以便满足使用 SAML 作为标准的机构要求。

#### 验收标准
1. 当管理员配置 SAML provider（IdP 元数据、SP 证书）时，系统应当完成 SP-IdP 元数据交换并校验 IdP 签名证书链。
2. 当 IdP 通过 POST binding 回传 SAML Response 时，系统应当校验 XML 签名与（如启用）加密断言，签名或断言校验失败则拒绝登录。
3. 如果部署环境缺少 `xmlsec1` 系统库或对应 wheel（信创 CPU 架构常见），那么系统应当在启动自检或 provider 测试连接时给出明确的缺依赖错误，而不是在登录时才失败。
4. 系统应当始终把断言校验通过后的用户映射、会话签发、吊销委托给 `w3-04` 已交付的机制。

### 需求 3：LDAP/AD 适配器（若行方选择 LDAP/AD）

**用户故事：** 作为行内运维人员，我希望 Octop 能直接对接行内 LDAP/AD 目录做口令校验，以便沿用现有目录服务而不引入额外的联合认证组件。

#### 验收标准
1. 当 `config.auth_backend` 配置为 `ldap` 且用户提交用户名口令登录时，`UserManager.authenticate` 应当在本地口令校验之外（或之前）尝试对配置的 LDAP/AD 服务器执行 bind 校验。
2. 如果 LDAP bind 失败（凭据错误或服务器不可达），那么系统应当拒绝登录并返回统一的鉴权失败错误，不泄露 LDAP 侧具体失败原因。
3. 当 LDAP bind 成功且用户在本地不存在时，系统应当按配置的属性映射规则自动开户或拒绝（取决于 `auto_provision` 配置），并把 LDAP 属性映射到角色。
4. 系统应当始终对 LDAP 连接使用 TLS，且不把 LDAP 明文凭据写入日志或 `audit_log`。

### 需求 4：SM2 签名协作（若 IdP 要求国密验签）

**用户故事：** 作为安全合规负责人，我希望 CAS/SAML 适配器在 IdP 使用 SM2 签名时能正确验签，以便满足密评对国密算法的要求。

#### 验收标准
1. 当 IdP 元数据或票据声明使用 SM2 签名算法时，适配器应当调用 `p2-02` 暴露的国密验签接口完成校验，不在本 spec 内重复实现 SM2 原语。
2. 如果 `p2-02` 尚未合入，那么本 spec 在需要 SM2 验签的部署中应当明确阻塞并在设计文档中记录依赖，不允许静默跳过签名校验。

### 需求 5：协议互斥与按需实施

**用户故事：** 作为项目排期负责人，我希望三种适配器各自独立估算工作量，以便只实施行方最终选中的那一种。

#### 验收标准
1. 系统（本 spec 的文档与任务清单）应当始终把 CAS、SAML、LDAP 三个实施单元相互独立列出，互不产生代码依赖。
2. 当行方最终确认协议后，实施方应当只按对应需求（需求 1/2/3 之一）落地，未选中的协议不产生任何代码改动。
