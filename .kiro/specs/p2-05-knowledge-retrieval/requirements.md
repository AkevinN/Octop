# 需求文档：知识库检索重写与三级权限

> spec：`p2-05-knowledge-retrieval` ｜ 波次：二期 ｜ 基线：`757fd12` ｜ 预估：35 人日
> 前置：`w3-03-authorization-foundation`、`w2-03-database-adaptation` ｜ 全局约束：`.kiro/steering/intranet-transformation.md`

## 引言

现状（基线 757fd12 已核实）：`index.py` 每库一个独立 SQLite 侧车，检索时全表 `SELECT`（≈L110，无 WHERE 无 LIMIT）+ Python 侧算余弦排序；无全文检索、无中文分词、无重排；切分是定长滑窗（`chunk.py`，800 字/120 重叠）；权限只有『私有 / 全实例共享』两档（`repos/knowledge.py:178`），HTTP/IM/定时三条检索入口各自读这份权限，语义耦合但不统一收口。

为什么做：银行内网断外网、有等保与密评要求。全表算余弦在十万级 chunk 时要反序列化数百 MB 向量；两档权限无法支撑"部门共享但非全员可见"；检索必须能离线运行。

范围内：检索层重写（索引 schema、混合检索编排、切分策略、中文分词、RRF、可选重排）、知识库三级 ACL（`visibility` + 授权表，统一 `list_visible` 单一 SQL 覆盖 HTTP/IM/定时三条路径）、检索侧审计、v1→v2 索引迁移与后台自动重建、控制面数据库 fork 迁移（`visibility` 列 + `knowledge_base_grants` 表）。

范围外（归其他 spec）：
- 全局断网开关定义、`onnx_download.py`/`onnx_service.py` 的"运行期下载全部关闭"消费改造 —— 归 `w2-01`（steering §3）；本 spec 只假定该开关已生效。
- `list_visible` 的 admin 绕过删除、权限判定收口、角色三员分立 —— 归 `w3-03`；本 spec 只在其产出上叠加 `visibility`/`grants`。
- 控制面数据库方言定稿、DDL 导出、连接池参数 —— 归 `w2-03`。
- 向量数据入信创库（PG 向量后端必做）、国密算法、KMS —— 分别属未来立项与 `p2-02`；本 spec 默认向量留在 SQLite 侧车。
- fork 迁移 runner 本体、i18n overlay 深合并机制、`CHANGELOG-intranet.md`/`docs/api-intranet.md` 骨架 —— 归 `w0-01`/`w0-04`；本 spec 只消费其产出。
- 能力开关框架 —— 归 `w1-02`；rerank 能力探测复用它。

## 需求

### 需求 1：混合检索取代全表扫描

**用户故事：** 作为知识库使用者，我希望大库检索不必每次读出全部 chunk，以便响应时间可控、内存占用不随库增长线性放大。

#### 验收标准

1. 当某知识库 chunk 数达到万级时，检索应当只反序列化候选上限内的向量条目，而不是全表。
2. 当查询同时命中字面相关与语义相关的不同文档时，系统应当通过 RRF 融合让两类命中都出现在结果中。
3. 如果同分命中需要排序，那么融合结果应当按确定的 tie-break 规则稳定，不依赖字典/集合迭代顺序。
4. 系统应当始终保留旧版 `chunk_text()` 签名与返回形状不变，供既有调用方（如索引重建任务）继续使用。

### 需求 2：中文可检索

**用户故事：** 作为使用中文业务文档的用户，我希望用 2-4 字的中文关键词就能检索到相关段落，以便不必输入完整句子。

#### 验收标准

1. 当文档写入索引时，系统应当对中文文本做应用侧分词并写入可供全文检索的列。
2. 当用户以短中文词（如『贷款』『利率』）查询时，系统应当返回包含该词的文档片段。
3. 如果目标运行环境的 SQLite 未编译 FTS5，那么字面检索通道应当整体降级为纯向量检索，而不是报错或返回空结果。

### 需求 3：结构感知切分

**用户故事：** 作为文档上传者，我希望切分不要从句子或表格行中间截断，以便召回的片段语义完整。

#### 验收标准

1. 当切分 Markdown 文档时，系统应当不在标题内部切断，并在每个片段的 meta 中记录标题路径。
2. 当切分中文长段时，系统应当优先在『。！？；』或换行处断开，不产生半句。
3. 当切分表格/CSV 解析产出的整行文本时，系统应当不从行中间切开。
4. 系统应当始终对相同输入产生相同的切分结果（幂等）。

### 需求 4：知识库三级权限

**用户故事：** 作为知识库所有者，我希望能把库授权给指定同事只读或可编辑，而不必开放给全实例，以便满足部门间最小可见范围的要求。

#### 验收标准

1. 当知识库 `visibility` 为 `private` 时，系统应当只允许所有者与有效授权对象访问。
2. 当所有者对某用户授予 `reader` 授权时，被授权用户应当能够 list/read/检索该库，但不能上传或删除文档。
3. 当授权被撤销时，被撤销用户应当立即不再能看到该库。
4. 当知识库 `visibility` 为 `org` 时，其可见范围应当与旧版 `shared=1` 等价。
5. 系统应当始终通过 repo 层单一 SQL（`list_visible`）决定可见性，HTTP 检索、IM 网关、定时投递三条入口应当看到完全相同的可见库集合。

### 需求 5：v1 索引自动迁移

**用户故事：** 作为运维人员，我希望升级后旧知识库不需要手工点重建，以便平滑上线。

#### 验收标准

1. 当系统在启动时识别到某知识库索引仍是 v1 格式（缺少 `schema_meta` 或版本号过低）时，系统应当自动把该库文档标记为待重建并入队处理。
2. 在重建完成之前，该知识库的检索应当能正常降级工作或明确标记为不可用，不应静默返回全空且不留痕迹。
3. 当重建完成时，系统应当将文档状态置回 `ready` 且 `chunk_count > 0`。

### 需求 6：检索审计与可选重排

**用户故事：** 作为合规负责人，我希望知识库检索行为可审计、重排服务不可用时不影响正常问答，以便满足密评与业务连续性要求。

#### 验收标准

1. 当一次检索发生时，系统应当写入一条 `audit_log`，payload 含 `kb_ids`、命中 `doc_id` 列表与命中条数，不含 chunk 正文与完整查询词。
2. 如果承载检索的 services 缺少 `audit_repo`（如测试替身），那么检索应当照常完成，不应因缺属性而抛异常。
3. 如果配置的重排服务超时或返回异常，那么系统应当降级为仅 RRF 顺序返回结果，不应抛错中断整轮检索。
4. 当重排未配置时，`capability` 接口应当返回 `rerank.enabled=false`，且检索行为应当与仅开启 RRF 时完全一致。
